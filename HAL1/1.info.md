# MicroXR Light Health HAL — Detailed Data-Flow Analysis

## 1. Scope

This document describes the runtime data flow implemented by the files under `hal-server/microxr-light-health`. It follows the current code as written, from Android service startup through LED/ALS interaction, health classification, and listener notification.

The implementation has five main layers:

1. **Android init and VINTF** start and declare the HAL.
2. **AIDL Binder service** accepts health-check requests and listener registrations.
3. **Worker thread** serializes long-running health checks outside Binder threads.
4. **Device-I/O adapter** translates generic core callbacks into Light Behaviors Binder calls and Sensor NDK operations.
5. **Core algorithm** collects ALS samples, detects differential spikes, and returns a health status.

## 5. Trigger scheduling and coalescing

`triggerHealthCheck()` does not perform hardware access on a Binder thread. It calls `requestHealthCheck()`, which updates guarded state and wakes the worker.

```text
                         triggerHealthCheck()
                                  |
                                  v
                 +----------------------------------+
                 | Lock worker_mutex_               |
                 |                                  |
                 | requested OR running ?           |
                 +----------+-----------------------+
                            |
                 +----------+----------+
                 | Yes                 | No
                 v                     v
        +------------------+   +--------------------------+
        | Coalesce trigger |   | check_requested_ = true  |
        | Return OK        |   | notify worker condition  |
        +------------------+   +------------+-------------+
                                            |
                                            v
                                      +-----------+
                                      | PENDING   |
                                      | req=true  |
                                      | run=false |
                                      +-----+-----+
                                            | worker wakes
                                            v
                                      +-----------+
            additional trigger ----> | RUNNING   |
               is coalesced           | req=false |
                                      | run=true  |
                                      +-----+-----+
                                            | runHealthCheck returns
                                            v
                                      +-----------+
                                      | IDLE      |
                                      | req=false |
                                      | run=false |
                                      +-----------+

 Shutdown from IDLE or PENDING:
   stopping_=true -> notify worker -> worker observes stopping_ -> exits

 Shutdown while RUNNING:
   stopping_=true -> active check finishes -> next worker-loop test exits
```

### Scheduling rules

1. With no pending or running check, a trigger sets `check_requested_ = true`.
2. If a request is already pending, another trigger is acknowledged but does not add another job.
3. If a check is running, another trigger is also acknowledged and coalesced.
4. The worker clears `check_requested_` and sets `check_running_` before hardware work starts.
5. After `runHealthCheck()` returns, the worker clears `check_running_` and then notifies listeners.
6. Because `check_running_` is cleared before listener notification, a trigger received during notification can create the next pending check.

This produces at most one pending/running health-check operation under the state represented by the two flags.

### ALS selection

1. The sensor list is scanned for `ASENSOR_TYPE_LIGHT`.
2. Sensor names are converted to lowercase.

5. The selected sensor is enabled on an event queue attached to a camera looper.
6. The requested event rate is set from `max(ASensor_getMinDelay(sensor), 0)` microseconds.

## 8. C callback bridge between core and Android I/O

The core library does not directly depend on C++ service objects. It receives a C-compatible operations structure:

```c
MicroXrLightHealthOps {
    context,
    set_led,
    set_led_solid_red_white,
    read_als
}
```

`context` points to the current `LightHealthDeviceIo` instance. Static bridge functions cast it back to that instance and invoke the corresponding method.

```text
                  MicroXrLightHealthOps passed to core
 +------------------------------------------------------------------------+
 |                                                                        |
 |  context -------------------------------> LightHealthDeviceIo*         |
 |                                                                        |
 |  set_led --------------------+                                         |
 |                              v                                         |
 |                    setLedCallback(context, enabled)                    |
 |                              | cast context                             |
 |                              v                                         |
 |                    DeviceIo::setLed(enabled)                            |
 |                    - drain old ALS events                              |
 |                    - call ILightBehaviors                              |
 |                                                                        |
 |  set_led_solid_red_white --+                                          |
 |                              v                                         |
 |                    setLedSolidRedWhiteCallback(context)                 |
 |                              | cast context                             |
 |                              v                                         |
 |                    DeviceIo::setLedSolidRedWhite()                      |
 |                    - drain old ALS events                              |
 |                    - call ILightBehaviors                              |
 |                                                                        |
 |  read_als -------------------+                                         |
 |                              v                                         |
 |                    readAlsCallback(context, timeout, lux*)              |
 |                              | cast context                             |
 |                              v                                         |
 |                    DeviceIo::readAls(timeout, lux*)                     |
```

| Core callback | Instance method | External operation |
|---|---|---|
| `set_led(context, true)` | `setLed(true)` | Drain queued ALS events, then request WORLD_FACING `SOLID` with color `0x00FF0000`. |
| `set_led(context, false)` | `setLed(false)` | Drain queued ALS events, then request WORLD_FACING `OFF`. |
| `set_led_solid_red_white(context)` | `setLedSolidRedWhite()` | Drain queued ALS events, then request WORLD_FACING `SOLID` with color `0x00FF6464` and `numCycles = 0`. |
| `read_als(context, timeout, &lux)` | `readAls(...)` | Read/poll the sensor queue until a light event, timeout, or error. |

Draining the ALS event queue immediately before each LED command removes already-queued sensor events from the previous LED state.

## 9. Current core phase flow

The default algorithm configuration is:

| Parameter | Value |
|---|---:|
| Blink cycles | 3 |
| Phase 1 duration | 1 second (`led_off_duration`) |
| Phase 2 duration | 1 second (`led_on_duration`) |
| Phase 3 duration | 1 second (`led_off_duration`) |
| Maximum samples per phase | 15 |
| Differential threshold | 2000 lux |
| Spike time-difference tolerance | ±50 ms |

The core contains a file-scope `healthySimulation` Boolean initialized to `false`. The LED commands actually issued in both modes are:

| Phase | Log/semantic label | `healthySimulation == false` (current default) | `healthySimulation == true` |
|---|---|---|---|
| 1 | Solid red | `set_led(false)` → OFF | `set_led(true)` → solid red |
| 2 | Solid red + white | `set_led(false)` → OFF | `set_led_solid_red_white()` → `0xFF6464` |
| 3 | LED off / baseline | `set_led(false)` → OFF | `set_led(true)` → solid red |

The Boolean is internal to the core source and is not part of the public C API or `AlgorithmConfig`.

### Aggregate result across three cycles

- The aggregate starts as `MICROXR_LIGHT_HEALTH_TAMPERED`.
- A cycle that satisfies all spike conditions changes it to `MICROXR_LIGHT_HEALTH_HEALTHY`.
- It is not reset to `TAMPERED` by a later non-matching cycle.
- Therefore, the normal completed result is `HEALTHY` if at least one of the three cycles passes; otherwise it is `TAMPERED`.
- Validation failures, LED callback failures, and ALS read failures return `UNKNOWN` immediately.

## 10. ALS sample acquisition in one phase

```text
 CollectPhase(duration, sample_count=15)
                   |
                   v
         deadline = now + duration
                   |
                   v
       +---------------------------+
       | Have 15 samples already?  |
       +------+--------------------+
              | Yes                         | No
              v                             v
    sleep until deadline          +-------------------+
              |                   | now >= deadline?  |
              |                   +------+------------+
              |                          | Yes -------------------+
              |                          |                        |
              |                          v No                     |
              |           remaining_ms = deadline - now          |
              |                          |                        |
              |                          v                        |
              |           read_als(remaining_ms, &lux)            |
              |                          |                        |
              |             +------------+-------------+          |
              |             |                          |          |
              |          success                 -ETIMEDOUT       |
              |             |                          |          |
              |             v                          +----------+
              |       lux is finite?                              |
              |        | Yes   | No --> return false               |
              |        v                                           |
              |  append lux and pre-read timestamp                 |
              |        |                                           |
              |        +---------------> loop                      |
              |                                                    |
              +----------------------------------------------------+
                                   |
                                   v
                              return true

 Any nonzero read result other than -ETIMEDOUT -> return false
```

### Timeout propagation

For every requested sample:

1. The core computes the milliseconds remaining before the phase deadline.
2. It clamps that value to at least 1 ms and at most `UINT32_MAX`.
3. `LightHealthDeviceIo::readAls()` first tries `ASensorEventQueue_getEvents()`.
4. If no event is ready, it calls `ALooper_pollOnce_camera()` using the remaining timeout.
5. A valid `ASENSOR_TYPE_LIGHT` event returns `event.light` as the lux value.
6. Looper timeout becomes `-ETIMEDOUT`; looper/event errors become `-EIO`.
7. A phase-level `-ETIMEDOUT` is treated as completion of the phase with the samples already collected.
8. If all 15 samples arrive before the phase deadline, the core sleeps until the deadline so that each phase retains its fixed duration.

Each stored sample time is captured immediately before calling `read_als()`. The lux value is appended after the callback returns.

## 11. Differential-spike data path

After the three phases of one blink, up to 45 lux readings and timestamps are available in acquisition order.

```text
ordered_samples = [s0, s1, s2, ... sN]
sample_times    = [t0, t1, t2, ... tN]

difference[i] = ordered_samples[i] - ordered_samples[i - 1]
```

The core scans from index 1 through the final sample:

- The **first positive spike** is the first `difference > 2000.0f`.
- The **last negative spike** is updated whenever `difference < -2000.0f`.
- Spike timestamps use `sample_times[i]`, the timestamp associated with the newer value in the difference.

A blink is classified as matching when all of the following hold:

1. A positive spike exists.
2. A negative spike exists.
3. The negative spike occurs after the positive spike.
4. Positive spike elapsed time from `blink_start_time` is 1000–1050 ms inclusive.
5. Negative spike elapsed time from `blink_start_time` is 2000–2050 ms inclusive.
6. Negative-minus-positive spike time is within `led_on_duration ± 50 ms`, which is 950–1050 ms with the default configuration.

`AlgorithmConfig` contains `differential_threshold`, initialized to `2000.0f`. The active comparisons in `RunWithConfig()` use the file-level `kDifferentialThreshold`, which has the same default value.

`CalculateTrimmedMean()` is implemented as an internal helper but is not called by the active `RunWithConfig()` data path. The current classification uses adjacent raw lux differences rather than phase means.

## 12. Result conversion and final LED handling

When `microxr_light_health_core_run()` returns, `LightHealth::runHealthCheck()` performs a final `setLed(false)` before exposing the result.

```text

             +--------------------------+

             | final explicit OFF       |

                          |

              | success               | failure
              v                       v
 +--------------------------+   +--------------------------+

 |                          |   | UNKNOWN                  |

              +---------------+--------------+
```

Status conversion is direct:

| Core C enum | AIDL enum sent by service |
|---|---|
| `MICROXR_LIGHT_HEALTH_HEALTHY` | `LightHealthStatus::HEALTHY` |
| `MICROXR_LIGHT_HEALTH_TAMPERED` | `LightHealthStatus::TAMPERED` |

- Device-I/O initialization returns a nonzero result.
- Core returns `UNKNOWN`.
- The explicit final LED-OFF operation fails.

## 13. Listener registration and notification flow

### Registration

```text
 registerHealthListener(listener)
                  |
                  v
          +------------------+
          | listener is null?|
          +----+-------------+
               | Yes ---------------------> EX_ILLEGAL_ARGUMENT
               |
               v No
     +-----------------------------+
     | Same Binder already stored? |
     +------+----------------------+
            | Yes ------------------------> return OK, no new callback
            |
            v No
     AIBinder_linkToDeath(cookie)
            |
      +-----+-------------------+----------------+
      | STATUS_OK               | INVALID_OP     | other error
      v                         v                v
 store listener + cookie    store listener   return Binder status
      |                     without cookie
      +-----------+-------------+
                  |
                  v
      copy current_status_ while locked
                  |
                  v
      release listener_mutex_
                  |
                  v
      listener->onLightHealth(current_status_)
                  |
                  v
               return OK

 Completed check:                       Remote Binder death:

 result                                 onListenerDied(cookie)
   |                                      |
   v                                      v
 lock listener_mutex_                   lock listener_mutex_
 update current_status_                 remove matching listener
 copy listener vector                   remove matching cookie
 unlock                                 unlock
   |
   v
 call onLightHealth(result)
 on each copied listener
```

`current_status_` begins as AIDL `UNKNOWN`, so a newly registered listener receives the most recently stored status immediately, even before the first completed check.

### Completed-check notification

1. The worker calls `notifyListeners(result)`.
2. Under `listener_mutex_`, the service updates `current_status_` and copies `listeners_`.
3. It releases the mutex.
4. It invokes `onLightHealth(status)` on each copied listener.
5. Callback failures are logged; subsequent listeners are still invoked.

Callbacks are deliberately made after releasing `listener_mutex_`, so listener Binder calls do not execute while the listener collection is locked.

### Unregistration and Binder death

- Explicit unregistration locates entries by `AIBinder*` identity.
- If a death cookie exists, it unlinks the death recipient and removes the cookie.
- It then removes the listener.
- If a remote listener dies, `onListenerDied()` removes matching listeners and cookies under `listener_mutex_`.

```text
 +----------|------------------------------------------------------------+
            |
            v
 +--------------------------+
 | Listener Binder endpoints|
 +--------------------------+

 worker_mutex_ protects:
   stopping_, check_requested_, check_running_

 listener_mutex_ protects:
   current_status_, listeners_, listener_cookies_
```

### Guarded state

| Mutex | Protected data |
|---|---|
| `worker_mutex_` | `stopping_`, `check_requested_`, and `check_running_` |
| `listener_mutex_` | `current_status_`, `listeners_`, and `listener_cookies_` |

The hardware/core operation runs only on the dedicated worker, so the normal service path does not run two health checks concurrently. Binder calls remain available for triggering, registration, and unregistration while the worker performs the approximately nine-second three-cycle algorithm.

## 15. Per-check object lifetime and cleanup

`LightHealthDeviceIo` is stack-allocated inside `LightHealth::runHealthCheck()` and therefore has one lifetime per check.

```text
 +----------------------------------+
 | Construct LightHealthDeviceIo    |
 +----------------+-----------------+
                  |
                  v
 +----------------------------------+
 | Connect to Light Behaviors       |
 +----------------+-----------------+
                  |
                  v
 +----------------------------------+
 | Select and enable ALS            |
 | Create looper and event queue    |
 +----------------+-----------------+
                  |
                  v
 +----------------------------------+
 | Core uses DeviceIo callbacks     |
 +----------------+-----------------+
                  |
                  v
 +----------------------------------+
 | Service requests final LED OFF   |
 +----------------+-----------------+
                  |
                  v
 +----------------------------------+
 | DeviceIo destructor              |
 |                                  |
 | led_may_be_on_ == true ?         |
 |     request LED OFF again        |
 +----------------+-----------------+
                  |
                  v
 +----------------------------------+
 | Disable selected sensor          |
 | Destroy sensor event queue       |
 | Release camera looper            |
 | Clear sensor pointers            |
 +----------------+-----------------+
                  |
                  v
 +----------------------------------+
 | Release shared Binder references |
 +----------------------------------+
```

Cleanup behavior is:

1. If the Light Behaviors interface exists and `led_may_be_on_` is true, the destructor requests LED OFF.
2. If the sensor was enabled, it disables the sensor.
3. It destroys the sensor event queue.
4. It releases the camera looper.
5. It clears sensor pointers; shared Binder references are released with the object.

On the normal completed path, `runHealthCheck()` requests LED OFF before the object leaves scope. The destructor provides an additional conditional OFF path based on `led_may_be_on_`.

## 16. Condensed end-to-end trace

1. Android init starts the vendor service executable.
2. The process starts an NDK Binder pool with a maximum of two threads.
3. `LightHealth` starts its worker and registers `ILightHealth/default`.
4. A client registers a listener and immediately receives `current_status_`, initially `UNKNOWN`.
5. A client calls `triggerHealthCheck()`.
6. The Binder method sets one pending-request flag and returns immediately.
7. The worker wakes, marks the check running, and validates core API version 2.
8. A per-check device adapter connects to `ILightBehaviors/default`.
9. It selects the preferred `tsl2511` light sensor or falls back to the default light sensor.
10. It creates/enables an ALS queue and builds the C callback table.
11. The core performs three blink cycles, each with three one-second sampling phases.
12. Before each LED command, queued ALS events are drained.
13. During each phase, the core requests up to 15 lux samples using deadline-based timeouts.
14. The core computes adjacent lux differences across the ordered samples for each cycle.
15. It searches for a first positive spike and a last subsequent negative spike above/below ±2000 lux.
16. It compares those spikes with absolute and relative timing windows.
17. At least one matching cycle yields `HEALTHY`; no matching completed cycle yields `TAMPERED`; operational failures yield `UNKNOWN`.
18. The service requests a final LED OFF.
19. The C result is converted to the matching AIDL enum.
20. The device adapter disables and destroys its ALS resources.
21. The worker stores the result as `current_status_` and calls every registered listener.
22. The worker returns to its condition-variable wait state.
